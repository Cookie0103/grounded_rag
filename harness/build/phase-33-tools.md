# 阶段 33：模拟业务系统与工具层

## 需求

### 目标

1. 一个独立的模拟业务系统 `mock_core/`（FastAPI + MySQL），带可复现的合成数据和故障注入。
2. 问答服务侧的 5 个只读工具，全部经过统一中间件：鉴权 → 缓存 → 调用 → 字段白名单 → 截断 → 记录。

### 非目标

- 让模型决定调哪个工具（阶段 34）。
- 任何写接口。

### 验收标准

| 编号 | 标准 | 验证 |
|---|---|---|
| AC1 | `mock_core` 一条命令建表并灌入种子数据；同一种子两次生成的数据逐行相同 | 两次导出的哈希 |
| AC2 | 种子数据覆盖：420 行还款计划、ペアローン、延滞中、已完济、固定期间一年内到期、部分固定金利特约 | 统计脚本输出 |
| AC3 | 5 个接口都是 GET，缺坐席 ID 头返回 401 | API 测试 |
| AC4 | 中间件每一环有独立的单元测试 | 测试清单 |
| AC5 | 非归属坐席查客户：工具返回「拦截」，下游接口没有被调用 | 测试里断言调用次数为 0 |
| AC6 | 同一坐席 5 秒内重复查询命中 Redis；换一个坐席不命中 | 集成测试 |
| AC7 | 口座番号、住所、電話番号等敏感字段在工具输出里不存在 | 对每个工具的输出做字段断言 |
| AC8 | 420 行的还款计划经工具返回后不超过约定上限，并带 `total` | 测试；记录裁剪前后的 token 数 |
| AC9 | 注入超时或 5xx 时，工具在超时预算内返回「失败」，带原因，不抛未处理异常 | 集成测试 |
| AC10 | `poe check`、`poe test-int` 通过 | 命令输出 |

## 任务

- [ ] T1 `mock_core/`：独立的包和启动命令（compose 里加服务）；MySQL 表结构用迁移或建表脚本管理；和问答服务不共享代码，只通过 HTTP 交互。
- [ ] T2 种子生成器：固定随机种子，约 300 个客户、20 个坐席；还款计划按等额本息算出，利率条件和优惠与公开层里的商品结构对得上（商品名、金利类型、団信种类取自作者保存的页面）。
- [ ] T3 故障注入：按接口配置额外延迟、超时比例、5xx 比例，支持固定种子；提供管理接口或环境变量切换，评测时可按用例开关。
- [ ] T4 `app/tools/`：工具定义（名称、日文描述、参数 schema、字段白名单、列表上限）与中间件链；复用 `core/resilience.py` 的超时、重试、熔断；缓存后端用 Redis。
- [ ] T5 工具结果的数据结构：`ok` / `denied` / `failed` 三态，带 `data`、`total`、`reason`、`cached`、`elapsed_ms`，供后面的降级判断和数字溯源使用。
- [ ] T6 trace：每次工具调用记一条步骤详情（复用现有 `Step` / `StepDetails`，按需扩字段）。
- [ ] T7 import-linter 的分层约束里加入 `tools` 层。
